## Ownership transfer and quarantine

`server/internal/databases.OwnershipService` exposes `POST databases/{id}/owner-transfer`. Input is expected generation/policy epoch, nullable previous-owner reference, new application-local auth subject and agent policy `revoke|rebind-reviewed`. Only that application's superuser or an instance operator explicitly entering the application can invoke it. A new owner must be a live auth record in the same application; an organization/tenant key is not an auth subject. Cross-application moves use application export/import, not this endpoint.

Persist a transfer intent and fence the DB under its lifecycle/policy guard. Advance policy epoch and revoke old owner/grant/agent access before replacing ownership. Drain/cancel stale mutations and streams. Retain all records/files and the DB identity/generation. Bind the new owner, apply only explicitly selected grants, reconcile agent bindings and mark the intent complete. Default agent policy revokes affected bindings. Pending jobs are cancelled or explicitly rebound by kind; actor fields never silently change identity. Resume after a crash from the recorded intent; never leave both owners authorized during a partial transfer. A quarantined/unowned DB remains inaccessible until this procedure validates and returns it to ready. Idempotency includes old/new owners and the guarded epoch. Test removed owners, colliding IDs, revoked streams, unknown commit outcomes and restart between each step.

## Reference-copy refresh

`server/internal/referencecopy.Service` stores a versioned policy: source collection, allowed nonsecret field IDs, record selection AST, destination selector/template, delete behavior `remove-copy`, maximum lag and schema revision. Application auth/secrets are forbidden projections. The primary within this application remains authoritative. `_mb_reference_policies` stores definitions; `_mb_reference_targets` stores target generation, last applied sequence, policy revision and failure. Default maximum healthy lag is 60 seconds.

The source CDC commit schedules a durable refresh intent. A shared worker reads a consistent authorized source snapshot and upserts/deletes the exact read-only projection in bounded target transactions, recording source sequence and policy revision with each committed batch. An older event cannot overwrite a newer sequence. Duplicate execution is safe. Unknown outcomes reconcile the target checkpoint. New targets first receive a snapshot and then post-boundary changes; policy edits invalidate old refresh work and rebuild projections. Source deletion removes the copy; incompatible schema quarantines the projection and reports failure. No refresh changes authorization using cached membership or copied secrets. Reads that require a healthy copy return `reference_stale` when its declared lag is exceeded; diagnostics show the source/target sequence. Native/offline replicas receive only the declared projection. There is no cross-file atomic freshness claim.

## Qualified relations, cascades and reports

Ordinary relations remain same-context record IDs. A global relation declares `global:true` and resolves a permitted collection in the current application's primary; the normal rule/field mask is reevaluated for the actor. A qualified relation declares an explicit destination database in its schema and stores references with databaseId, generation, collectionId and recordId. No applicationId override is accepted. The schema validates destination collection/type and prohibits cross-context native joins or ordinary atomic cascades.

`server/internal/relations.Resolver` performs bounded secondary authorized reads. A request is limited to 100 expanded references, depth 6 and its normal deadline; excess returns `relation_limit`, not a partial result described as complete. Filter traversal compiles to a bounded authorized key lookup before local SQL; if the plan cannot satisfy the bound it fails with an exact policy error. It never scans all private databases. Cross-application record relations are not implied.

An explicit cascade workflow definition lists allowed destination contexts, relation fields, actions and authorization principal. The durable workflow captures expected source/target versions, applies deterministic per-context steps and records completed/failed results. Cancellation preserves committed steps. No cross-context ACID promise exists. Without this definition the schema rejects a cross-context cascade before activation.

Application-wide reporting uses an approved report definition with source templates, projected nonsecret fields, aggregate query, actor policy, freshness bound and target shared collection. `server/internal/reports.Service` consumes CDC into a primary-owned aggregate through idempotent per-source checkpoints, not unbounded fan-out during a frontend request. Deletes/revocations require aggregate recomputation or policy reset before exposure. Report output rules still filter readers. Define/rebuild/status operations are privileged; source credentials and membership fields cannot be inferred from report rows. These are application-local workflows, not authorization to combine unrelated applications.

## Safe layout transitions

`server/internal/setup.LayoutMigration` reuses the import mapping/copy/validation service against a coherent snapshot of the current application. Input binds current application/database generations, source policy revision, destination layout, ownership/membership plan, template and verified recovery backup. A dry run inventories actual rows/files and all shared/qualified dependencies. Stage unpublished destination roots and candidate policy/route epoch; verify canonical per-context hashes, rules and auth fixtures. Fence affected writes, reconcile the final snapshot boundary, publish through the application journal and invalidate old context tokens/cursors. Split/merge has no silent duplication, owner guessing or automatic inverse after accepted writes. Failure before active publication preserves the old layout; failure after it preserves new accepted writes and requires reconciliation. Never translate a config toggle directly into a data move.

## Live-query definitions

`server/internal/livequery.PlanRegistry` stores `_mb_live_plans` keyed by application-local name and immutable revision, with SQL AST/hash, typed parameters, result key/shape, dependencies, policy plan, row/byte limits, state and creator. Only an application superuser can create, publish or retire a definition. Five operations are list, create revision, get revision, publish and retire. SQL must prepare read-only in the actual profile, be deterministic, expose a unique non-null result key and permit collection/field policy injection. A privileged SQL plan cannot be exposed as an ordinary record subscription.

Ordinary `live.register` resolves a published query ID/revision and instantiates it under the actor's current rules. Parameter and shape mismatches fail before subscription allocation. Publishing a revision does not mutate the SQL of an existing instance. Retiring a revision sends a reset/termination to its subscribers; incompatible schema/policy does likewise. Snapshot/CDC race handling, keyed deltas, bounded replay and restart reset follow integration-contracts.md. Plan storage, compile errors, retirement and wrong-app query IDs are acceptance requirements, not just the streaming endpoint.

## Rollout selection and controls

`template.rollout` accepts either explicit IDs (up to 10,000 per request) or a structured app-local target selector over kind, state, owner, profile, template and revision. It cannot accept raw SQL. Persist the selection hash and stream the fixed ID/generation snapshot into `_mb_schema_rollout_targets` in bounded batches; do not keep millions of IDs/results in a JSON column or resident array. New databases created after the snapshot are not retroactively added.

`rollout.pause` stops new target admission and safely completes/rolls back current native steps. `rollout.resume` requires the recorded selection/revision and revalidates each target generation. `rollout.retry` selects failed targets with their recorded errors and deterministic step IDs; succeeded targets are not migrated twice. `rollout.targets` pages exact per-target states/results. Cancel is terminal for remaining work and does not undo completed targets. Changed/deleted/incompatible targets receive an explicit failed or skipped-with-reason result, never success. Resume/retry cannot invent a passed result after manual file replacement.

## Sync retention and local identity

Server receipts retain the documented seven-day deduplication window. The SDK stores its deadline with pending groups and never blindly resubmits an uncertain expired group. It queries available status, compares the fresh authorized base, preserves the original intent and marks unresolved effects `outcome_unknown` for explicit reconciliation. New IDs are not generated to disguise a retry. Missing receipt history is not evidence of rollback.

Deletion markers remain until explicit `compact-sync` maintenance. That job fences the DB, takes/verifies a coherent backup, snapshots all present record versions and data, creates a new database generation, drops only obsolete deleted-version/change/receipt history, validates contents and publishes using the restore journal. All old cursors, clients, staged mutations and native revisions must bootstrap against the new generation. Nondeleted versions remain. Old-generation pushes fail before mutation, so a deleted record cannot be resurrected by a stale client. Automatic retention does not remove tombstones independently. Clients preserve/export unsent edits before reconciling a new base.

## Resources and fair admission

`server/internal/admission.Manager` owns dynamic process and application budgets. Defaults: 64 managed DB handles, 16 active application metadata leases, 8 concurrent opens, 256 actual SQL connections, 128 active foreground queries, 16 per application, 2 background workers, 1024 queued jobs globally and 128 per application. Reserve 16 connection slots for auth/instance/recovery work; pool maximums are ceilings, not preallocated connection promises. Every real connection acquires an aggregate token before opening. A cold app's primary/auxiliary handles are included; default startup does not reserve full-sized pools for every possible app.

Foreground admission is round-robin among applications with one FIFO queue per app. Background work uses separate slots and cannot consume the recovery reservation. Queue wait defaults to five seconds then returns retryable resource_exhausted. Native allocator/page-cache requests are accounted before allocation through the owned bridge's budget checks; aggregate lazy native cache budget is 256 MiB. The JS pool has at most four leased VMs and a 64 MiB admission/high-water estimate, measured from the shared Go heap. Goja has no assumed public per-VM hard heap limiter: apply invocation deadlines/interrupts, bounded input/results and the process soft memory limit; report overshoot. Trusted extension code is not a hostile-code memory sandbox. A process OOM affects all applications and must be recorded honestly in qualification.

Disk accounting includes DB, WAL/revert WAL, FTS, files, staging, trash and recovery copies, including remote-object bytes separately. Free-space admission keeps a default 1 GiB reserve and checks available inodes where supported. Staging reserves declared bytes before transfer; concurrent requests update a durable reservation ledger. Per-app/per-DB operator byte limits default unset, not a vendor database-count cap. WAL soft warning defaults 256 MiB per DB; inability to checkpoint safely causes bounded backpressure rather than deleting active logs. Reconcile reservations after crash. Config schema and diagnostics expose every budget and usage category.

## Restore authority, audits and schema definitions

Restore-to-new requests explicitly choose owner/grant policy `remove` or `preserve-authorized` plus reviewed destination subjects. Default is remove; preserved subjects must exist in the selected application and are reauthorized before publication. Application imports never preserve instance-operator authority. Archives bind application identity/generation, artifacts, full file coverage and secret/key dependencies. Required external keys are verified before activation; keys are not embedded by default. A one-app restore must not rotate another app's keys or routes.

Administrative audit records go to app-local auxiliary storage, or instance metadata for instance actions. Record application, actor, operation, target/generation, canonical request hash, outcome and timestamp; redact values/secrets. Default retention is 90 days or 256 MiB per scope with explicit floor reporting. Operational logs retain inherited settings and do not become a compliance certification.

Schema operations are discriminated contracts, not unrestricted objects: collection definitions use the pinned collection/field schema plus engine-reference.md; index definitions specify kind, fields/expressions, uniqueness/predicate and options; type definitions identify base/constraints/members; view definitions specify query/result key/dependencies/materialization; sequence definitions specify integer start/increment/min/max/cycle. Each kind is validated by its resolver before SQL effects, including generated per-collection wire schemas. Unknown keys and unknown kinds fail. Stored definitions are revision/hash bound and included in backup/portable export.

## Acceptance ownership

MB-OWNERTRANSFER, MB-REFERENCE, MB-RELWORKFLOW, MB-LAYOUT, MB-LIVEPLAN, MB-ROLLOUTCTL, MB-SYNCCOMPACT and MB-FAIRNESS each require positive target-state assertions, wrong-application/actor negatives, concurrency, cancellation and restart tests. Qualification must observe transferred ownership, actual refreshed rows/deletes, authorized relation/report results, unchanged layout hashes on failed publication, real live-plan retirement, per-target rollout results, rejection of old-generation resurrection and fair bounded resource use under contention. Document checks are not substitutes for these runs.


## Metadata publication details

Each activation stores the starting commit sequence for every activated target. Any later committed target mutation conservatively forbids snapshot rollback, even if its response was lost. The check is performed under the lifecycle guard against actual target state; an asynchronous instance counter is not authority to discard a commit. Cross-file registry/filesystem recovery follows the journal and never assumes an unrecorded rollback.
