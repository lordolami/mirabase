# MiraBase v0.1 build contract

**Current release authority:** [current implementation inventory](../current-product.md), [user documentation](../user/index.md) and [launch status](../launch/status.md). Initial v0.1/roadmap delivery labels below preserve planning contracts; they do not establish today's implementation or permit deleting subsequently integrated features. [Managed cloud](../cloud/README.md) has separate design and gates.

This document defines the current release. [Roadmap](roadsmap.md) owns later delivery. The detailed chapters retain the complete product design; only the portions selected here and in the release allocation are v0.1 commitments. A roadmap feature is not a failed v0.1 gate, and passing v0.1 does not establish completion of the full product.

## What users receive

One lightweight, self-hosted PocketBase-style backend, extended with Turso. One process serves one application and can give each user, tenant or agent a private database. Developers retain collections, records, authentication, rules, files, realtime, the existing dashboard, SDK methods and Go/JavaScript extensions.

The application has one shared identity/settings/schema boundary. A tenant is a school, company or workspace whose members share data; a user is an account; an agent is a separate scoped identity. Several unrelated applications with separate settings, auth and trusted code belong to the roadmap. There is no process per database and no vendor database-count quota.

## First-time developer workflow

1. Download the qualified executable and run `mirabase serve`. The default shared application needs no config, tenant catalog or cloud account. Create the first superuser through the inherited setup and open `/_/`.
2. Create auth and ordinary collections, configure rules, files/email and frontend hosting as usual. Shared layout needs nothing else.
3. Optionally open Storage setup. Choose user, tenant or agent storage, select existing auth/tenant/membership fields and choose the private collection template. The preview explains the binding and expected DB count; it never guesses from field names.
4. Publish the validated policy. An empty target layout can be activated; moving existing populated shared collections is refused with `layout_migration_required` and a link to its roadmap contract. Existing data remains unchanged. Adding independent empty private collections alongside populated shared collections is permitted after dependency validation.
5. A verified account, tenant or agent is bound once to a database. Lazy first access provisions it durably. Joining an existing tenant reuses its database. Concurrent first requests converge on one binding, not duplicate files.
6. Connect the frontend using normal collection methods and an immutable context/tenant option. Browse databases and their records/files through the existing dashboard. Ordinary users receive only their authorized resources.
7. Back up and verify recovery. When moving to a larger server, transfer the whole application state and required secrets, verify destination behavior, then switch traffic. Copying only one `data.db` is insufficient.

Invitations in v0.1 can be application logic using inherited auth/mail/hooks and normal membership CRUD. The generic built-in invitation API, its token lifecycle and generated invite workflow are roadmap work. Current membership checks and protection against client-created privilege elevation are release gates now.

## Isolation and extension rules

Use the immutable default `ApplicationContext` with ID `default` from the beginning. Resolve the database and current authority before rules/forms/hooks/files/SSE/search. Preserve application-qualified identity in persisted keys to support later app isolation. Do not install `instance.db`, independent-app routes or per-app runtime objects in v0.1.

`X-MiraBase-Database` and the reviewed `X-MiraBase-Tenant` selector follow [partitioning](partitioning.md). Invalid or unauthorized selection never falls back to primary. Multiple eligible tenants require a choice; one tenant may be the configured default. Files and SSE use purpose-bound context tokens when headers are unavailable. Rules, hidden fields, file protection and revocation apply on every new path.

Accounts/settings/memberships stay in primary. Private DBs contain only their published collection set and required local metadata. Ordinary same-file relations remain unchanged. Explicit primary references use bounded secondary reads under current rules, at most 100 references and depth 6. Arbitrary filter joins, views, uniqueness or cascades crossing files fail policy validation before activation. A private unique index is private, not application-global. Do not silently rewrite an existing global uniqueness promise.

Keep one router, scheduler, bounded worker pool and JS pool. Bound Go/JS helpers to the current invocation; no mutable process-wide selected database. Trusted hooks retain their privileges and unsafe external-effect retry boundary. The basic agents feature gives scoped identities and databases; it provides no AgentFS workspace, autonomous execution or model hosting.

## Search and schema boundaries

The search operation accepts `vector` and `text` modes only. Use the exact [search contracts](queries-and-search.md), including rule filtering, field protection, finite vectors, dimensions/metrics, tokenizer/Unicode behavior, stable ties, budgets, cursor invalidation and real index rebuild recovery. `hybrid` and `fuzzy` requests return the explicit release-capability error before query allocation; no partial substitute is advertised.

Native FTS and vector functions are included in the qualified payload. Broader relational functions may execute in the privileged SQL console if the actual engine supports them, but this does not promise the roadmap typed-field, richer-SQL, transport or schema services. SQL console writes remain administrative and do not claim record validation or record SSE.

Managed templates are immutable revisions. A basic rollout snapshots explicit target IDs/generations to durable rows, validates actual data, applies with bounded concurrency, and reports every target. Never retain an unbounded target array or mark mixed revisions complete. Existing public collection updates affecting managed templates must create a guarded rollout or refuse before changing schema; no successful primary-only edit may strand private DBs silently. A failed rollout resumes from its journal through job recovery; rerunning failed targets requires revision/generation guards. Advanced selectors and pause/resume/retry management endpoints are roadmap work.

## Required safety primitives

Durable lifecycle jobs, target-local idempotency receipts, transaction outcomes, monotonic mutation boundaries, file-finalization intents, encrypted built-in delivery intents and recovery journals are included whenever a v0.1 operation needs them. Implement these at their first consumer. Deferring the general workflow/callback product does not defer crash safety, single-use auth flows or built-in mail retry discipline. External delivery remains at least once with deduplication identifiers; arbitrary custom-hook I/O is never automatically replay-safe.

No public CDC, retained change stream or offline replica is included. Inherited SSE remains transient. Internal commit counters and job journals can supply backup/cutover/FTS coordination without promising public replay. Every supported write path, including privileged SQL and trusted framework SQL, must advance the committed-mutation boundary atomically; rollback checks cannot rely on SSE or a process-memory counter. Native capture functions may be used internally if needed and must then be tested. Their presence does not establish the roadmap CDC family.

Coherent backup uses maintenance, drained leases/finalizations, closed persistent state, exact native file manifests, hashed copies and isolated restore verification. It covers WAL/MVCC and FTS artifacts. Windows uses tested stop/restore/start. Generation changes revoke old leases/tokens and invalidate cursors. No rollback can discard a target mutation committed after activation, including a commit whose HTTP response was lost.

Default admission retains 64 managed handles, 8 concurrent opens, 256 actual SQL connections with 16 reserved for auth/recovery, bounded query/worker queues, 2 background workers and a 1 GiB disk reserve. Idle handles are evictable; leased transactions are not. Preserve all applicable [resource contracts](implementation-closure.md#resources-and-fair-admission); multi-application fairness is roadmap work, while fairness among this application's target DBs is required now.

## PocketBase shared-layout adoption

Use the source acquisition, copy, validation and publication machinery in [PocketBase import](pocketbase-tenant-import.md), narrowed to `shared` layout and one default application. Accept the pinned baseline only. A historical version must first use the documented supported upstream upgrade; do not label it universally compatible.

Validate archive paths/hashes/integrity, source settings encryption and current migrations. The read-only SQLite reader operates on a verified session-owned source copy and is never the live provider. Copy actual rows and file bytes, preserve stable IDs/hashes/token keys/rules/settings, inventory remote S3 coverage, review hook/migration path mappings and disable outbound effects during validation. A settings/key or required-file failure prevents activation.

Preview actual collection/record/file totals and hashes, account behavior, SQL compatibility and required artifact/endpoint changes. Stage and validate the whole shared application, require the exact report/revision, then use a durable guarded cutover journal. Preserve the source and old target. Resume/cancel/recover without duplicates or discarded acknowledged writes. The dashboard, CLI and HTTP service use the same implementation. Schema-only import never claims full adoption success.

The split/tenant ownership editors, account/rule transformation engine, per-tenant preview and tenant route publication are roadmap work. The shared-layout request rejects those options explicitly and directs users to the roadmap; it does not silently import them into shared storage.

## Exact implementation surfaces

[Roadmap operation allocation](roadsmap.md#operation-allocation) labels every additive operation. Inherited routes remain required. The full [wire schemas](wire-schema-reference.md) remain the canonical superset; release constraints narrow allowed enums/options at validation, document generation and SDK typing, never silently ignore extra fields.

For v0.1, intersect request/response schemas with these constraints: application ID is `default`; search mode is `vector|text`; importer destination/layout is default/shared; setup accepts shared/user/tenant/agent only without populated-data relocation; field definitions accept inherited kinds plus vector; template/rollout and jobs expose released kinds only; grants accept record/file/database-inspect scopes only. `changes.read`, `record.sync`, raw SQL and native-replica credentials are not granted. Existing record auth and separate agent identities provide remote authentication. Native SQL console access remains superuser-only.

Export/import additive operations are roadmap portable typed-data operations. v0.1 server moves and target export use verified native backup archives through backup operations and the offline restore command; do not advertise a native archive as the future typed cross-engine export. Agent binding, ownership recovery and basic lifecycle can use the full applicable schemas under the narrowed scopes.

### Configuration

The [configuration reference](configuration-reference.md) is the full-product schema. Produce the v0.1 effective schema by retaining `formatVersion`, `engine`, `databases`, `partitioning`, `jobs`, `search`, `security`, `shutdown`, `imports`, `admission` and `audit` with their current defaults and bounds. Keep the `applications` block only with `defaultApplicationId=default`, `maxActiveMetadata=1`, `routeMode=prefix`; this is a forward-compatible fixed boundary, not an independent-app service. `bootstrapTokenSeconds` applies only if used by inherited setup integration.

Omit `changes`, `sync`, `postgres`, `sqlHttp`, `liveQueries`, `membership` and `references` from the accepted v0.1 schema. Explicit use of these future keys is a configuration error naming the roadmap feature, including false-valued keys; absence is the default. Do not accept switches that imply shipped functionality. UI/API examples must use the release schema. Preserve inherited settings encryption and secret references; native page encryption/key rotation is later work.

### Native ABI and artifacts

Required owned ABI groups are version/build manifest/buffer release; DB/connection/statement open/info/bind/step/close; I/O poll/cancel; transaction begin/commit/rollback; DB quiesce/persistent manifest; memory usage/budget. `mb_capture_configure/read` are internal requirements only if selected for commit-boundary/index correctness. PG-session and native-sync codec/pull/checkpoint symbols are roadmap ABI groups, excluded from the v0.1 required-symbol probe. Mark build groups explicitly; never install no-op functions pretending success.

One payload includes required SQLite frontend, core functions, vector, FTS, WAL/MVCC and platform I/O. PG frontend, native replication, custom codecs and extension-load interfaces can be omitted from this release build. Do not remove core dependencies required by included features. Six server targets remain Linux/macOS/Windows on amd64/arm64. Every advertised artifact must pass real target runs; no successful cross-compilation alone qualifies it.

### Storage and upgrades

Install application/target tables only at their first released consumer: DB/grant/agent registries, templates and per-target rollout rows, lifecycle/jobs/receipts, schema journals, shared-import sessions/cutover, tenant route/binding policy, resource reservations and mutation boundaries. The full [storage reference](storage-format-reference.md) is a catalog of exact definitions, not an instruction to create all tables. Instance/multi-app tables, sync/retention/local-client tables, reference/report/live-plan tables and invitation tables are roadmap storage. Native internal tables needed by the engine are separate.

The full-product resource reservation definition references the instance application registry. In v0.1 place this table in the default application's primary DB with the same columns/indexes, `application_id TEXT NOT NULL CHECK(application_id='default')` and no foreign key to an absent `_mb_applications` table. On consolidation upgrade, quiesce reservations, reconcile actual files/jobs, import them into the instance registry transactionally and retire the app-local reservation table only after matching hashes/counts; never count or release the same reservation twice.

Target-local `_mb_mutation_boundary` contains one row: `id INTEGER PRIMARY KEY CHECK(id=1)`, `sequence INTEGER NOT NULL CHECK(sequence>=0)`. Install it when guarded lifecycle/import publication first needs it. The provider/coordinator increments it once in each committed target mutation transaction, including administrative SQL and schema changes; internal receipt-only bookkeeping is excluded. Journal publication records the boundary and generation. A post-publication boundary change forbids snapshot rollback. Existing mutation capture may supply this signal, but public CDC storage/retention is not required. Rebuilds preserve it; restore gives a new generation with its validated boundary. Integrity tests must demonstrate raw/trusted SQL cannot commit around this guard.

For shared PocketBase plans, use the existing `ImportPlanDraft` with `layout=shared`, `namespace=shared`, `tenantKind=null`, `tenantSource=null`, `access=null`, `selector={kind:none,source:null}` and one `placement=shared` entry for every source collection. Preserve account policy and global uniqueness exactly; reject any ownership split, reference-copy adaptation or nonempty tenant adaptation. Actual preview has tenantCount=0, referenceCopies=0, sharedRecords=sourceRecords=assignedRecords and no unassigned/conflicting records. Retain exact schema field names and JSON string quoting in generated requests; these prose values are constraints, not a replacement wire encoding.

`ImportCreate.targetMode` accepts `new-application` only for the initially empty default root, and `replace-application` for a guarded default-root replacement. Reject `append-application`, batch/source reservation fields and any destination other than `default`; no instance revision is required. Shared placements use `ownership.kind=shared`, `referenceFieldIds=[]`, `uniquePolicy=preserve-global`, `adaptationIds=[]`. Account policy explicitly chooses `preserve-if-compatible|revoke-existing` sessions and `retain-destination-superuser|use-source-superuser`; validate the retained/selected administrator before activation and state session invalidation in the preview. Never silently preserve incompatible tokens or remove the last administrator.

Persist `applicationId=default` where defined; reserve internal names. Optional storage activation remains lazy. No empty placeholder sync/catalog tables are a feature. Install owned migrations with schema checks and recoverable publication; do not edit an existing released migration. Later releases add metadata and adapters without silently repartitioning data or changing ownership. Preserve origins, DB IDs/generations, collection/record IDs, auth/rule semantics, files, manifest/backup versions, SDK methods and selector contracts. Engine/format upgrades require verified backup and qualified migration; replacing the executable is not an automatic downgrade path.

## Release gates

1. Pinned untouched PocketBase reference and legal notices; actual branded CLI/UI/SDK builds.
2. Real native provider, trusted payload tamper negatives, handle/statement lifetime, cancellation, fault and packaging tests.
3. Complete inherited suite and real API/UI/SDK/auth/files/mail/hooks/migrations parity on Turso, with documented canonical-DDL adaptations and real maintenance behavior.
4. Two auth collections with colliding IDs, Alice/Bob, two agents and a multi-member tenant: simultaneous REST/files/SSE/search must remain isolated, including after eviction/reopen, restore and revocation.
5. Real provisioning/delete/quarantine/reassignment/schema-rollout/backup/import jobs interrupted at each journal/filesystem/publication/response boundary; verify rows, files, hashes, generations and recovery.
6. MVCC conflicts/savepoints/retry and uncertain commits; no duplicate external side effects or accepted-write loss. WAL/MVCC backup restore and FTS/vector correctness must be exercised together where advertised.
7. Shared-layout PocketBase adoption from actual directory and backup, with bcrypt login, token/rule/settings/migration/file preservation, malformed archives, wrong keys, cancellation, response loss and unsafe rollback negatives.
8. Fresh machine installation, signed update verification, offline restore, complete server move and measured footprint/startup/load on every qualified target. Apply the existing 40 MiB compressed / 96 MiB executable / 160 MiB installed / 96 MiB idle targets to the whole v0.1 deliverable; no claim they have been achieved.
9. Every v0.1 allocation has implementation symbols and executed evidence. Scoped families record the specific release slice; they stay incomplete at full-product level until their roadmap remainder passes. Deferred requirements never receive fabricated passes.
